# Voxel Storage Core — архитектура нового террейна

Статус: **рабочая спецификация, первая реализация**
Ветка: \`feature/voxel-storage-core\`
Область: только хранение и изменение воксельных данных. Рендеринг, мешинг, GPU, камера и LOD в эту подсистему не входят.

## 1. Цель

Построить адресуемый трёхмерный мир \`N × Y × N\`, пригодный для игровых операций:

- рытьё окопов, подвалов и сквозных тоннелей;
- локальное разрушение взрывами;
- создание нависающих масс, пещер и сложного рельефа;
- хранение разных горных пород и локальных материальных жил;
- быстрые точечные запросы и пакетное чтение/изменение пространственных областей;
- компактное представление больших однородных объёмов.

Источник истины — логическое воксельное пространство. Поверхностная сетка, полигоны и графические буферы являются производными представлениями и не принадлежат storage core.

## 2. Координаты и смысл вокселя

- Логические координаты целочисленные: \`(x, y, z)\`.
- Ось Y — вертикальная.
- Начальное физическое разрешение: **0,1 м на воксель**. Параметр задаётся экземпляру хранилища, но после создания мира не меняется.
- Воксель — ячейка пространства. Он не обязан отображаться отдельным кубом.
- Геометрия хранится как скалярное поле, семплированное в центрах ячеек.
- Материал относится к объёмной ячейке и хранится отдельно от геометрического поля.

Положительная плотность означает твёрдую массу, отрицательная — воздух, ноль — границу. Геометрическая поверхность может проходить между центрами ячеек.

## 3. Разделение каналов

### 3.1 Geometry / Density

Первый формат — квантованный усечённый signed distance:

- тип: \`short\`;
- положительное значение: внутри твёрдого тела;
- отрицательное: снаружи;
- ноль: изоповерхность;
- масштаб первой реализации: 256 единиц на метр;
- дальние значения насыщаются диапазоном \`short\`.

Полное точное расстояние нужно только возле поверхности. В глубине твёрдого тела или воздуха достаточно правильного знака и значения насыщения.

Геометрические примитивы объединяются операциями над полем с положительным знаком внутри:

- Union: \`max(current, shape)\`;
- Difference: \`min(current, -shape)\`.

Первая реализация поддерживает Box, Sphere и Capsule. Это компактные описания объёмов, а не отдельный рендер-меш.

### 3.2 Material

- тип: \`ushort MaterialId\`;
- \`0\` зарезервирован для воздуха/отсутствия материала;
- свойства породы (плотность, твёрдость, сопротивление взрыву, стоимость копания и т. п.) находятся в общей таблице материалов, а не дублируются в каждом вокселе.

Материальный канал независим от геометрического. Рудная жила может менять Material ID, не меняя Density. При чтении ячейки с отрицательной плотностью возвращается MaterialId=0.

## 4. Представление данных: процедурная основа + компактные регионы + bricks + локальные edits

Storage использует неизменяемую базовую основу и локальный слой изменений. Основа может состоять из одного процедурного 3D-источника, компактных геометрических/материальных операций и импортированных точных voxel-bricks. Импортированный brick имеет приоритет над источником и примитивами в своих 16³ координатах; edit-brick имеет приоритет над всем базовым содержимым.

### 4.1 Base Volume — компактное описание исходного мира

Геометрия задаётся ограниченными трёхмерными примитивами с AABB:

- Solid Box / Sphere / Capsule;
- Subtract Box / Sphere / Capsule.

Материалы задаются отдельными ограниченными областями окраски (Box / Sphere / Capsule).

Таким образом, большое плато можно задать одним объёмным Box, а не миллионами одинаковых записей. Рудная жила — материальной областью, а тоннель — вычитанием Capsule/Box. Запрос отдельного вокселя вычисляет значение логической решётки в его центре.

Для ускорения поиска примитивы индексируются по пространственным bucket-ам размером 256³ вокселей (25,6 м на сторону при voxel size 0,1 м). Индекс хранит ссылки на примитивы, пересекающие bucket. Brick 16³ выровнен и целиком помещается в один такой bucket, поэтому при пакетном чтении список кандидатов получается один раз на brick, а не на каждый воксель.

Base Volume строится до \`SealBase()\`. После фиксации базового объёма его примитивы неизменяемы. Это позволяет читать базовую геометрию параллельно без блокировок, пока не выполняется изменение edit-слоя.

### 4.2 Procedural Base Source — вычисляемая 3D-основа

`SetBaseSource(IVoxelBaseSource)` назначает один неизменяемый источник исходного объёма. Он отвечает за `Sample(x,y,z)`, при необходимости переопределяет пакетные `ReadRegion/ReadDensityRegion/ReadMaterialRegion` и может доказать однородность через `TryGetUniformRegion`. Это путь для больших seed-based миров, слоистой геологии, шума, подземных полостей и других сложных 3D-функций без материализации миллионов bricks.

Источник обязан быть детерминированным, потокобезопасным для чтения и не создавать объекты на каждый сэмпл. Его `TypeId` и `DataVersion` идентифицируют алгоритм/формат параметров. При `Save` источник записывает свои настройки; при `Load` вызывающий код передаёт `VoxelBaseSourceResolver`, который восстанавливает нужный класс. Без resolver загрузка файла с процедурным источником завершается понятной ошибкой. CSG-операции и материальные области применяются поверх source, импортированный Base Brick заменяет его в своём brick.

### 4.3 Dense Base Bricks — произвольные детализированные базовые данные

Импортированный базовый brick принимает два точных плоских массива по 4096 элементов: `short[4096]` и `ushort[4096]`. После импорта проверяется однородность: если все ячейки имеют одинаковую пару Density/Material, массивы отбрасываются и в памяти остаётся один `VoxelSample`. Только неоднородный brick сохраняет оба массива. Это путь для зон, где сложная геометрия или геология уже рассчитана генератором. Воксели внутри неоднородного brick доступны прямым индексом; при пакетном чтении строки копируются непрерывными диапазонами. `BaseDenseBytes` считает только полезную память массивов, не учитывая метаданные словаря и объектов.

### 4.4 Persistence — компактный бинарный snapshot

`Save(Stream)` записывает gzip-сжатый binary snapshot версии 3:
- размеры мира, размер вокселя, revision и sealed-state;
- базовые Geometry/Material operations;
- импортированные Base Bricks;
- только реально материализованные Edit Bricks и их независимые каналы.

`Load(Stream)` восстанавливает те же данные и пересобирает пространственные bucket-индексы. Однородный Base Brick сохраняется одной парой значений; неоднородные bricks и edit-каналы сохраняются массивами. Пустые области не сериализуются как массивы. Формат имеет magic signature и версию. История undo/redo в первой версии не сохраняется.

### 4.5 Edit Volume — локально материализованные данные

Изменения хранятся в разреженном словаре bricks размером **16³ вокселей** (1,6 м на сторону при текущем разрешении).

У brick два независимых канала:

- \`short[4096]\` — выделяется только когда в brick меняется геометрия;
- \`ushort[4096]\` — выделяется только когда меняется материал.

При первой записи в канал массив целиком заполняется значениями соответствующего базового канала: сначала из импортированного Base Brick, иначе вычисляется из базовых примитивов. Геометрические brush-операции записывают только значения в этой локальной полосе, поэтому их AABB с четырёхвоксельным padding содержит все затрагиваемые сэмплы; за пределами этого объёма усечённое поле не меняется. После этого запросы к изменённому участку читают обычный плоский массив с прямым индексом:

\`index = x + 16 * (y + 16 * z)\`.

Неизменённые области не получают edit-bricks. Пустой edit-слой не требует массива на каждый чанк мира.

Размер 16³ пока является инженерной отправной точкой, а не доказанным оптимумом. Позже сравнить 16³ и 32³ на сценариях взрыва, тоннеля и материальной жилы.

## 5. Операции и их стоимость

| Операция | Поведение |
|---|---|
| \`GetVoxel(x,y,z)\` | Сначала проверяет edit-brick, иначе вычисляет Base Volume по кандидатам текущего bucket |
| \`ReadRegion(bounds, spans)\` | Пакетно проходит область по bricks; кандидаты базовых примитивов находятся один раз на brick |
| Base Box/Sphere/Capsule | Добавляет одну запись примитива и индексы bucket-ов |
| Carve Sphere/Capsule/Box | Материализует только пересекаемые geometry-bricks и меняет значения в локальных массивах |
| Add Sphere/Box | Материализует только пересекаемые bricks; изменяет геометрию и при необходимости материал |
| Paint Material | Материализует только материальный канал затронутых bricks |
| Повторное изменение того же brick | Работает напрямую с уже выделенным массивом, без повторной материализации |

Точечный доступ нужен для небольших игровых запросов. Основной путь массовой обработки — \`ReadRegion\` и объёмные brush-операции, а не миллионы внешних вызовов \`GetVoxel\`.

## 6. Правила производительности и потоков

1. Нет объекта C# на каждый воксель.
2. Плоские массивы и простая адресация внутри dense-brick.
3. Геометрия и материалы выделяются и изменяются независимо.
4. Базовые большие области представлены примитивами, локальные исключения — bricks.
5. Нет обязательного полного разворачивания мира в Dense Grid.
6. Нет GPU readback: GPU не является источником истины.
7. Нет \`Thread.Sleep\`, \`Task.Delay\` или блокировок для покадровой синхронизации.
8. Первая версия имеет модель **single-writer**: редактирование выполняет владелец мира. Базовые данные неизменяемы после Seal. Чтение можно распараллеливать только пока нет одновременной записи в edit-слой. Для фоновых вычислений владелец мира заполняет caller-owned буферы через `ReadRegion` и передаёт их задачам; отдельный immutable snapshot API ещё не реализован. Общая блокировка всего хранилища не используется.
9. Пакетное чтение обрабатывает непрерывные участки памяти. Внешний код не должен делать отдельный межсистемный вызов на каждый воксель в горячем цикле.

## 7. Что эта модель описывает

- Большое ровное плато — один Box-примитив и Material ID.
- Порода/геологический слой — крупная материальная область.
- Рудная жила — отдельная материальная область; Density не изменяется.
- Подвал или тоннель — вычитание объёма из Density.
- Взрыв — локальное изменение geometry-bricks в пределах радиуса.
- Добавленная скальная масса — Union-примитив или локальный Add brush.
- Арки и нависающие массы — обычные трёхмерные объёмы; модель не ограничена одной высотой на X/Z.

## 8. Ограничения первой реализации

- Набор компактных базовых примитивов ограничен Box/Sphere/Capsule; сложные формы собираются CSG-комбинацией либо импортируются как точные Dense Base Bricks.
- Количество базовых примитивов в bucket напрямую влияет на стоимость вычисления Base Density. Нужны измерения и последующая локальная компактизация/запекание.
- Материальный brush в edit-слое материализует материальный массив brick целиком.
- Dense-brick 16³ ещё не прошёл benchmark против 32³.
- Первая версия не симулирует механику обрушения, перемещение породы, трещины, жидкости или деформацию материала как непрерывной среды.
- Сглаживание, извлечение поверхности, выбор триангуляции, нормали, GPU и LOD не входят в эту реализацию.

## 9. План верификации

Перед интеграцией с WorldMap выполнить storage-тесты:

1. Одно большое плато описывается одним примитивом; `TryGetUniformRegion` должен вернуть одну запись для большого внутреннего диапазона.
2. Процедурный источник создаёт сквозной тоннель в объёмной массе; точечное и пакетное чтение совпадают.
3. Save/Load восстанавливает `TypeId/DataVersion`, seed/параметры источника и поверхностные edit-bricks.
4. Пустой диапазон определяется как однородный без выделения edit-bricks.
5. Однородный импортированный brick занимает один sample без массивов; неоднородный хранит точные 4096 пар сэмплов.
6. Вычитание Capsule создаёт сквозной тоннель внутри плато.
7. Материальная жила изменяет только MaterialId, геометрия остаётся побитно прежней.
8. Локальное геометрическое разрушение материализует только пересекаемые bricks.
9. Материал не восстанавливается в пустой ячейке после повторного изменения плотности.
10. Пакетные Read-операции совпадают с точечным `GetVoxel` для primitive, procedural, uniform и dense base bricks.
11. За пределами edit-областей не выделяется память под edit-bricks.
12. Измеряются время точечного чтения, скорость ReadRegion, время первой материализации, повторного изменения и объём памяти.

Запуск проверок:

```powershell
dotnet run --project Core.Tests/Core.Tests.csproj --configuration Release
```

Отдельные измерения производительности:

```powershell
dotnet run --project Core.Tests/Core.Tests.csproj --configuration Release -- --bench
```

Рендерер в этих тестах не запускается и не изменяется.

## 10. Критерий принятия архитектуры

Система принимается только если:

- логически доступен каждый воксель фиксированной решётки;
- большая однородная область не требует массива всех своих вокселей;
- локальные операции не материализуют соседние/удалённые области;
- материал можно менять независимо от геометрии;
- подземные и нависающие объёмы адресуются тем же API;
- пакетное чтение не требует отдельного внешнего вызова на каждый воксель;
- измерения показывают приемлемые задержки и память на целевых сценариях.
