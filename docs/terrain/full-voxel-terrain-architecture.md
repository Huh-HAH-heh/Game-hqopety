# Полноценный воксельный террейн RimClone

## Цель

Террейн должен быть единым редактируемым трёхмерным полем, из которого строятся:
- видимая геометрия и LOD;
- горизонтальные и вертикальные срезы;
- столкновения и опорные поверхности;
- многослойная навигация.

Высоты поверхности, mesh и навигация не должны быть независимыми источниками истины.

## Что есть сейчас в `feature/raylib-terrain-renderer`

- `SparseVoxelStore` и параллельный interval backend удалены. `WorldMap.Voxels` — единственный владелец локальных 3D-изменений плотности и материалов.
- Базовая поверхность `WorldMap` остаётся компактной: плоские массивы высотных якорей и материалов на сетке 1 м по X/Z. Плотность базового поля вычисляется процедурно, а не хранится в полном 3D-массиве.
- Локальные деформации записываются в изотропную сетку 0,1 м внутри разреженных 16³ bricks. Каждый канал чанка адаптивен: отсортированные sparse-записи для малой заполненности, плотный массив с битовой маской после 2048 override-записей. При падении ниже половины порога `Compact()` может демонтировать канал обратно в sparse-форму.
- Размер логического voxel volume расширяемый. `ExpandVoxelWorld` добавляет пустое пространство без предварительного выделения массивов. Legacy tile/navigation grid пока сохраняет исходные границы.
- Сохранения voxel-изменений используют компактный формат v3; загрузчик принимает прежний v2 и переводит его в новое представление.
- Worker meshing получает immutable snapshot только затронутых storage bricks и halo, не читает живые изменяемые массивы.
- `VoxelTerrainRenderer` по-прежнему строит кандидатов на сетке 16³ с шагом 1 и пропускает погребённые вертикальные чанки по индексу потенциальных поверхностей. Многоуровневый sampling LOD ещё не реализован.
- `VoxelChunkMesher` сейчас greedy-mesher по byte MaterialId, а не SDF Marching Cubes/Dual Contouring. Он захватывает 18³ блоков на чанк с одновоксельным halo.

Это уже единое разреженное 3D-хранилище для деформаций, но не завершённая многоразрешающаяся voxel-world система.

## Референс Space Engineers: что именно копируем

Нужно копировать не внутренний код закрытого движка, а игровой результат и инструменты редактирования.

- В Space Engineers Voxel Hands дают набор объёмных форм: Box, Capsule, Ramp, Sphere и Terrain Auto Level. Игрок может добавлять, вырезать и заменять материал, не меняя форму.
- В Space Engineers 1 планетарная основа в основном heightmap-подобная. Поэтому она ограничивает естественные нависающие формы.
- В более новом VRAGE3 разработчики сохранили планетарную heightmap-основу и добавили небольшие voxel storage для нависающих скал и валунов. Это даёт полезный ориентир для RimClone: дешёвая базовая поверхность плюс локальные полноценные 3D-объёмы.

### Пространственная сетка

Базовая поверхность мира остаётся компактным источником высоты с текущей детализацией 1 м по XY. Полноценная кубическая 3D-сетка включается локально — внутри voxel storage, где нужны пещеры, нависающие скалы, валуны, тоннели и пользовательские деформации.

Внутри редактируемого voxel storage целевая базовая детализация — кубический воксель 0,1 x 0,1 x 0,1 м. Это согласуется с текущим шагом по вертикали, но не размножает 3D-сетку на весь планетарный объём.

Для всего мира 2304 x 2304 x 50 м такая детализация всё равно означала бы около 265 млрд потенциальных ячеек. Даже при разреженном хранении нельзя заранее материализовать каждый столбец. Поэтому база генерируется как heightmap/функция поверхности, а только области с реальными 3D-отклонениями материализуются в разреженные voxel storage.

### Хранение

- Пространственный адрес — целочисленные X/Y/Z voxel-координаты; размер storage brick — 16³ ячеек (1,6 м по ребру при шаге 0,1 м).
- Пустые storage bricks не создаются. В чанке отдельно хранятся overrides density samples и cell materials.
- Малозаполненный канал хранится отсортированными записями `(ushort localIndex, value)` с резервом capacity. Вставка не создаёт новый массив для каждого вокселя; capacity растёт геометрически. При 2048 overrides канал переходит в плотный flat array + битовую маску. Ниже 1024 overrides `Compact()` может вернуть его в sparse-представление.
- Density quantized в signed 16-bit. MaterialId — unsigned 16-bit. Это не резервирует полный массив в 16 КБ на каждый edit chunk: память зависит от количества override-значений, пока канал не стал плотным.
- Неизменённый базовый грунт не материализуется. Для текущего `WorldMap` он вычисляется из плоских height/material anchors на 1 м по X/Z; отдельные standalone поля могут передавать собственный 3D base sampler.
- Снимок мешера копирует только существующие override bricks в области чанка и halo. Рабочие потоки читают immutable snapshot; изменения мира не гоняются с чтением mutable storage.
- Save v3 сохраняет только отсортированные overrides, v2 читается через миграционный loader. Undo-снимки используют тот же compact entry layout.
- Логическое поле расширяется без realloc всего мира. Новые координаты по умолчанию пусты, а edit операции за пределами текущей границы увеличивают поле автоматически.

### Деформация

Все кисти работают с одним density field:
- CarveSphere / AddSphere — выкопать или добавить объём;
- CarveCapsule — траншея, тоннель или канал;
- Flatten / Plane — срезать или выровнять область;
- Smooth — сгладить переход;
- PaintMaterial — изменить материал, не меняя форму.

Для аддитивных и вычитающих операций применяется CSG над signed density, а не прямоугольная правка диапазонов по Z. Сглаживание должно быть отдельной операцией, чтобы обычное копание не размывало геометрию.

## Геометрия и LOD

- Геометрия строится из density field алгоритмом Marching Cubes или Dual Contouring. Выбор фиксируется после сравнения качества склонов, тоннелей и острых уступов на тестовых сценах.
- Нормали вычисляются из градиента density, а не назначаются только по шести направлениям.
- Чанк хранит mesh revision и revisions соседних границ.
- После редактирования перестраиваются только изменённые чанки и соседи, пересекающие границу.
- CPU-подготовка геометрии отделяется от GPU upload. Старый mesh остаётся видимым до готовности нового.
- Целевой вариант: базовая поверхность и локальные voxel storage получают независимые уровни данных. Для текущего Raylib backend это ещё не реализовано: он строит greedy-mesh на шаге 0,1 м. До внедрения LOD нельзя считать его стоимость ограниченной экранным размером.
- Срез строится из того же density field как 2D-контур/поверхность. Никакой второй независимой «крышки» из колонок быть не должно.

## Навигация из того же поля

Полную 3D-карту занятости хранить как плотную nav-матрицу нельзя. Для ходьбы нужна разреженная карта опорных поверхностей и связей между ними.

### Nav surface cell

Базовый горизонтальный шаг оставить 0,5 м на первом этапе. Внутри одной XY-ячейки разрешено несколько кандидатов поверхности на разных высотах.

Кандидат поверхности содержит:
- высоту пола и нормаль;
- свободную высоту над головой;
- уклон;
- материал/стоимость движения;
- признак опоры и проходимости;
- ссылку на voxel chunk и его revision.

Кандидат создаётся на границе solid/air, если нормаль и свободное пространство соответствуют профилю агента. Так мост и тоннель получают разные уровни навигации даже при одинаковых X/Y.

### Nav graph и матрицы

- Узел адресуется как (navX, navY, floorLayer), а не только (navX, navY).
- Рёбра создаются между соседними поверхностями с проверкой шага вверх/вниз, уклона, диагональных углов и clearance.
- Размеры и ограничения агента учитываются при построении профиля проходимости.
- Воксельные чанки имеют локальные nav-чанки и матрицы occupancy/cost/edge.
- Изменение density помечает dirty только соответствующие nav-чанки и соседей. Полная перестройка мира не выполняется.
- Для больших карт используется иерархия: сначала связи/порталы между nav-регионами, затем локальный A*.
- Результат маршрута должен содержать 3D-точки/высоты. Одни Vector2 waypoint недостаточны для многоуровневого мира.

## Порядок миграции

1. Закончить стабильность текущего среза и кэша мешей.
2. **Выполнено частично:** единый `SparseVoxelField` уже хранит 3D-изменения в adaptive sparse/dense bricks, а базовая heightmap остаётся процедурным источником. Следующий шаг — добавить явную многоразрешающуюся базовую плотность/макро-представление, не подменяя её мешами.
3. Добавить операции создания, вырезания, сглаживания, выравнивания и покраски локальных voxel storage; научить генератор создавать естественные места для навесов, скал и валунов.
4. Перевести рендер voxel storage на чанковую изоповерхность, halo и LOD seams. Высотная база и voxel storage должны стыковаться без щелей. Старый column mesher остаётся только переходным backend.
5. Перевести срез на density-plane и убрать колоночные cut caps.
6. Построить многослойный nav surface graph из того же density field; затем перевести UnitNavigationSystem на 3D route points.
7. **Выполнено для runtime-пути:** `SparseVoxelStore` удалён, `BlockTerrain` отвечает только за block-level и transitions. Совместимый `TileRange` API формируется из единого voxel field по запросу.

## Критерии готовности

- Можно вырезать сферой, капсулой и кистью произвольную форму.
- В одном XY-месте существуют мост, воздух под мостом и тоннель ниже.
- Чанки не имеют щелей при пересечении границ и смене LOD.
- Перемещение среза не создаёт мерцания, дыр и отставших крышек.
- Юнит проходит по мосту, под мостом и через тоннель как по разным уровням.
- Деформация перестраивает только локальные меши и nav-чанки.
- Отсутствуют плотные мировые массивы размера X*Y*Z.

## Справка по референсу

Space Engineers описывает Voxel Hands как инструмент изменения формы астероидов и планет: выемки, долины, скалы, заполнение кратеров и изменение материалов. Это нужный игровой результат; внутренняя реализация RimClone должна быть спроектирована под собственную плотность мира, навигацию и бюджет памяти.
