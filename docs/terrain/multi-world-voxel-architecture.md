# Много миров и полноценный воксельный террейн

## Требуемый результат

RimClone должен уметь одновременно содержать несколько самостоятельных ландшафтов — например, три астероида. Они существуют в одном игровом пространстве, попадают в один кадр рендеринга и обновляются одним циклом симуляции, но не делят между собой геометрию, повреждения, навигацию, юнитов и состояние мира.

Это не должно превращаться в три независимых окна, три игровых цикла или три копии графического рендерера.

## Аудит текущей реализации

### Что уже есть

- `WorldMap` — самостоятельный объект с собственными слоями, регионами, водой, блоками, версиями геометрии и навигации.
- `UnitSimulation.Update(WorldMap, deltaTime)` принимает карту мира явно. Отдельные экземпляры `UnitSimulation` могут работать с отдельными картами.
- `WorldMap.Voxels` — единый разреженный 3D density/material backend. Прежний `SparseVoxelStore` с вертикальными интервалами удалён из runtime-пути.
- Raylib-рендерер кэширует GPU-меши и использует GPU clip plane для горизонтального среза.
- В `Core/World/WorldSimulationGroup.cs` добавлен единый диспетчер, который обновляет несколько независимых пар `WorldMap + UnitSimulation` в одном вызове `Update`. У каждого мира собственные пауза и масштаб времени.

### Чего пока нет

1. `RaylibTerrainViewer.Run(WorldMap)` и `RaylibTerrainRenderer` пока рассчитаны на один `WorldMap`. GPU-кэши, LOD-состояние и массивы видимых регионов принадлежат одному экземпляру terrain snapshot.
2. Единый `SparseVoxelField` хранит редактируемые 3D overrides в 16³ bricks: малые каналы хранятся как sparse entries, заполненные переходят в dense flat arrays с битовыми масками. Процедурная база `WorldMap` остаётся компактной height/material anchors на 1 м по X/Z.
3. Текущий Raylib `VoxelChunkMesher` ещё не извлекает SDF-изоповерхность: он захватывает byte block IDs на Step=1 и строит greedy block faces. Многоуровневый sampling/LOD для него пока не реализован.
4. Существующая навигация и большинство игровых систем ещё не поддерживают произвольный набор независимых локальных систем координат.

Таким образом, текущий код — полезная переходная реализация, но не клон воксельной системы Space Engineers.

## Почему нельзя хранить весь объём плотным массивом

Для мира 2304 x 2304 x 50 м при кубическом шаге 0,1 м получается:

- X: 23 040 ячеек;
- Y: 23 040 ячеек;
- Z: 500 ячеек;
- всего около 265,4 млрд вокселей.

Даже по 4 байта на ячейку — примерно 1 ТБ без учёта индексов, мешей, навигации и служебных структур. Поэтому полный массив не подходит даже для одного такого мира, а для нескольких астероидов — тем более.

## Целевая архитектура

### 1. Локальный мир

Каждый ландшафт — отдельный экземпляр `VoxelWorld`:

- уникальный ID;
- локальная система координат;
- независимые данные вокселей и материалов;
- независимые версии изменённых чанков;
- собственная навигация;
- собственные юниты и состояние симуляции;
- transform в общей системе координат сцены.

Координаты вокселей остаются локальными. Перевод в общее пространство делается transform-матрицей на границе рендеринга и физики. Это не позволяет объектам одного астероида случайно менять координаты другого.

### 2. Разреженное адаптивное 3D-хранилище

Текущая реализация использует voxel coordinate step 0,1 м для локальных редактируемых данных, но не выделяет полный массив 16³ на каждый затронутый chunk:
- address — целочисленные X/Y/Z chunk coordinates;
- density sample overrides и cell material overrides хранятся отдельно;
- малозаполненные каналы — отсортированные flat sparse entries с геометрическим ростом capacity;
- при 2048 overrides канал переходит в плотный массив с bit mask;
- `Compact()` демонтирует dense-канал обратно в sparse при падении ниже 1024 entries;
- пустые bricks не создаются, empty bricks удаляются;
- snapshots для mesh workers копируют только реально существующие edit bricks в области и halo;
- save v3 хранит только overrides, а loader мигрирует старый v2 формат.

Для текущего `WorldMap` untouched base — компактные height/material anchors на сетке 1 м по X/Z, из которых density/material вычисляются при запросе. `ExpandVoxelWorld` расширяет только voxel volume: новые координаты — воздух, legacy tile/navigation map пока остаётся исходного размера.

Это первый этап адаптивного хранения. Он ещё не включает несколько полноценных resolution layers базовых voxel данных.

### 3. Деформация объёма

Все действия редактирования должны изменять один density field:

- вырезать сферу или эллипсоид;
- добавить объём;
- вырезать капсулу/тоннель;
- выровнять плоскостью;
- сгладить переход;
- изменить материал без изменения формы.

Геометрия, срезы, столкновения и навигация читают один источник данных. Не должно быть отдельного heightmap, который после выемки расходится с фактическим объёмом.

### 4. Один рендерер на все ландшафты

В окне существует один renderer и один проход камеры:

- один набор общих шейдеров и материалов;
- один атлас или таблица материалов;
- один вызов начала/окончания 3D-прохода;
- массив объектов ландшафта с transform;
- независимые GPU-кэши чанков каждого ландшафта;
- единый бюджет CPU meshing и GPU upload на кадр;
- приоритет загрузки по видимости, экранному размеру и расстоянию до камеры;
- отбрасывание объектов и чанков по frustum;
- отдельные LOD-состояния для каждого астероида;
- инстансинг/общие буферы там, где геометрия действительно повторяется.

Не следует создавать один renderer, material и shader на каждый астероид. Разделяются данные и кэши, но графический проход и общие GPU-ресурсы используются совместно.

### 5. Один цикл симуляции

`WorldSimulationGroup` — первый шаг к этой модели. Он уже принимает несколько независимых контекстов `WorldMap + UnitSimulation` и обновляет их одним вызовом.

Дальше каждый контекст должен получить:

- собственное локальное время и time scale;
- собственные юниты и физические тела;
- собственную гравитацию;
- локальную навигационную сетку;
- свои системы деформации и столкновений.

Для далёких миров нужен режим сна: не выполнять каждый дорогой этап с частотой активного мира. Частота обновления определяется активностью мира, а не количеством зарегистрированных астероидов. При этом глобальные часы и переходы между мирами должны оставаться детерминированными.

### 6. LOD и навигация

LOD относится к отображению, а не к источнику истины:

- расстояние влияет на выбор разрешения меша;
- LOD-швы закрывают переходы между уровнями;
- при смене LOD не меняется density field;
- мелкие детали не создаются, пока они не нужны камере.

Навигация строится из тех же вокселей, но отдельно кэширует поверхности опоры, высоту свободного пространства и связи между уровнями. Мост, пещера и поверхность над пещерой должны быть разными навигационными уровнями даже при одинаковых X/Y.

## Исправления среза в текущем коде

В текущем срезе была несогласованность границы: основной меш считал верхнюю границу solid-run включительно, а cut cap — строго. Для интервала `[StartZ, EndZ)` поверхность на плоскости `EndZ` должна закрываться.

Также прежняя сборка строила отдельный квад на каждый метровый столбец. Теперь соседние столбцы с одинаковым материалом объединяются в горизонтальные полосы, а обычные столбцы читаются из компактного snapshot без копирования всего массива TileRange. Лимит обновления крышек увеличен, потому что после объединения геометрии одна область стала дешевле в построении.

Это исправление относится к старому interval renderer. Оно не превращает хранилище в кубические 3D-воксели.

## План миграции

1. **Стабильность текущего среза.** Проверить совпадение границ, отсутствие чёрных областей, мерцания и резких пиков перестройки.
2. **VoxelWorld и 3D sparse chunks.** Ввести кубическое поле плотности рядом со старым хранилищем, добавить базовый генератор и операции CSG.
3. **Изоповерхность чанка.** Выбрать Dual Contouring или Marching Cubes; добавить halo, контроль границ и переходы LOD.
4. **Единая сцена.** Переделать renderer с одним графическим проходом и отдельными кэшами нескольких ландшафтов.
5. **Симуляция нескольких миров.** Расширить `WorldSimulationGroup` гравитацией, пространственными transform, сном далёких миров и переносом объектов.
6. **Навигация из density field.** Перенести поиск опорных поверхностей на многослойную локальную сетку.
7. **Удаление старого interval backend.** Только после переноса генерации, сохранения, навигации, столкновений и редактора.

## Критерии готовности

- В одной сцене видны минимум три самостоятельных астероида.
- У каждого астероида можно независимо вырезать тоннель, кратер и пещеру.
- Правка одного мира не меняет версии и данные другого.
- В одном кадре выполняется один 3D render pass, а не отдельный цикл на каждый мир.
- В одном simulation tick обновляются все активные миры.
- Далёкие неизменяемые миры могут спать и не пересобирать меши.
- LOD не создаёт швы, щели или дублированные поверхности.
- Срез не создаёт чёрные дыры при изменении высоты.
- Память растёт от материализованных/изменённых чанков, а не от полного объёма всех миров.
